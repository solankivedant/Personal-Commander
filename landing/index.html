01 · WHY LOCAL-FIRST

Everything a munshi handles stays with the munshi.

Files, Office documents, and email are exactly the things you don't hand to a stranger - so Munshiji runs entirely on this laptop's CPU and integrated graphics. No cloud round-trip is required for anything it does by default; the internet is opt-in, per feature, and only for what you explicitly allow.

02 · WHAT IT CONTROLS

Eight tool packs, one voice.

Each pack ships behind the same contract - a tier (what it can touch), a risk level (whether it asks first), and an undo. None are wired up yet; this is the shape the assistant is being built toward.

03 · HOW IT DECIDES

A cascade, not a chatbot loop.

Most assistants send every request to a language model and wait several seconds. Munshiji tries the cheap, deterministic paths first - a 3B model only gets involved when a request is genuinely compositional, and it never needs to for the four in five commands that aren't.

04 · WHAT IT WON'T DO WITHOUT ASKING

Shell access is the whole risk. These rules aren't optional.

Munshiji reads content written by strangers - web pages, email, PDFs - and has the ability to act on your machine. Treating a stray sentence in a fetched page as a command is the specific failure this is built to resist.

Untrusted content is never obeyed

Fetched pages, email, and PDFs are summarized and reasoned about - never followed as instructions.

Confirmation always comes by voice

Anything that deletes, sends, spends, or overwrites speaks its intent and waits for a spoken yes - a tool result can't trigger it directly.

Every mutation registers its undo first

The inverse operation is queued before anything runs, not after - up to 20 steps back.

Some things are structurally unreachable

Credential access, registry writes, and mass deletion aren't discouraged by a prompt - the LLM's tool path can't reach them at all.
